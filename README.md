# Hybrid RAG with LangGraph + Gemini + Milvus Lite (text + audio + image + video)

A minimal hybrid retrieval-augmented generation app:

- **Milvus Lite** — embedded vector DB (just a local `.db` file, no Docker/server)
- **Google Gemini** — `gemini-embedding-001` for embeddings, `gemini-flash-latest` for generation, native audio transcription, image *and* video understanding
- **LangGraph** — `[transcribe_question | interpret_image | interpret_video]` → `retrieve` → `rerank` → `generate`

Multimodal input: **text documents**, **audio clips**, **images** and **videos** are all ingested into the same collection and become searchable together. Queries can be typed, **spoken** (`data/audio_queries/`), **shown as an image** (`data/image_queries/`) or **shown as a video** (`data/video_queries/`, e.g. a narrated screen recording) — optionally with a caption. The graph turns them into text before searching.

## Setup

```bash
pip install -r requirements.txt
export GEMINI_API_KEY="your-key-here"   # https://aistudio.google.com/apikey
python main.py
```

Running `main.py` will:
1. Create a Milvus Lite collection with a dense field (Gemini embeddings), a sparse field auto-populated by Milvus's built-in BM25 function, and `modality`/`source` fields to track where each chunk came from
2. Load `data/test_data.json` (text docs), transcribe every clip in `data/audio/` (audio docs) describe every image in `data/images/` (image docs) and every video in `data/videos/` (video docs) with Gemini
3. Embed and insert all of them into one collection
4. Run 6 typed test questions through the LangGraph pipeline — including ones answerable only from audio, only from an image, and only from a video — and print the re-ranked chunks (tagged `text:`, `audio:`, `image:` or `video:`, with hybrid rank + re-rank score) plus the final answer
5. Run every spoken question in `data/audio_queries/` through the same pipeline (audio → transcribed question → hybrid search → answer)
6. Run every image in `data/image_queries/` twice — once with no caption, once with the caption "How do I fix this?" (image → interpreted question → hybrid search → answer)
7. Run every video in `data/video_queries/` (video → interpreted question from narration + on-screen text → hybrid search → answer)

If you ever change the schema or hit a Milvus error mid-run, delete the local DB before re-running so it rebuilds cleanly:

```bash
rm -rf hybrid_rag.db
python main.py
```

## Videos: ingestion and video search

Videos use the same pattern again, with one difference: Gemini sees the frames **and** hears the audio track, so one call captures both narration and on-screen text:

```
video file → Gemini (native video understanding) → transcript of speech + all on-screen text verbatim + summary
           → dense embedding + BM25 sparse vector → Milvus (modality="video")
```

`gemini_client.describe_video()` sends clips ≤ 20 MB inline; larger files go through the Gemini Files API (`client.files.upload`) and the helper polls until processing finishes. To add your own videos: drop `.mp4`/`.mov`/`.webm` files into `data/videos/` and rerun `python main.py`.

**Video queries** go through an `interpret_video` node. `gemini_client.describe_video_query()` turns the clip (+ optional caption) into one self-contained question — if the user *speaks* the question in the recording it uses that, and it pulls exact codes/names from what's on screen:

```python
app.invoke({"question_video": "data/video_queries/query_checkout_outage.mp4"})                                # narrated recording
app.invoke({"question_video": "data/videos/doc16_video.mp4", "question": "Who is the record holder?"})  # video + caption
```

Sample clips are narrated slideshows generated by `make_sample_videos.py`. `doc15_video.mp4` is an incident review for `ERR-4521`: every other ERR-4521 doc (text, audio, image) says what the code *means*, but the root cause (pool exhausted at 50) and the fix (raised to 200) exist **only in the video** — so *"What was the root cause of the ERR-4521 incident and how was it fixed?"* proves video ingestion contributes answers. The query clip `query_checkout_outage.mp4` shows the error on screen while the user asks the question out loud, so Gemini has to combine both channels to form the search query.

Because the dataset now has several ERR-4521 documents across four modalities, `retrieve` pulls a wider candidate pool and a re-ranker picks the best of them — see the next section.

## Re-ranking (two-stage retrieval)

Hybrid search is *recall*-oriented: dense + BM25 fused with RRF is cheap enough to run over the whole collection and reliably gets the right chunks into the top ~10, but RRF only knows *rank positions* — it can't tell that a chunk which merely shares keywords with the question doesn't actually answer it. A re-ranker fixes that by reading the question and each candidate **together**, which is far more accurate but too expensive to run over everything. So:

```
hybrid_search (dense + BM25 → RRF)  →  top-10 candidates
        → gemini_client.rerank()  scores each 0–10 in one listwise call (structured JSON output)
        → top-5 with score > 0     →  generate
```

The re-ranker is `gemini_client.rerank()` — an LLM re-ranker using the same Gemini model, so there are no extra dependencies and it works identically across all four modalities (everything is text by that point). `graph.py` adds it as a `rerank` node between `retrieve` and `generate`; `CANDIDATE_POOL` (10) and `FINAL_TOP_K` (5) are at the top of that file.

Turn it off to compare — both `main.py` and the server honour `RERANK=0`:

```bash
RERANK=0 python main.py
RERANK=0 uvicorn server:app
```

What it changes on the sample data (hybrid rank → re-rank score):

| Question | Hybrid-only top 3 | With re-ranker |
|---|---|---|
| *Is Java a drink or a programming language?* | doc3 (Java lang), **doc1 (Python)**, doc4 (coffee) | doc3 → 7, doc4 → 7; doc1 scored 0 and dropped |
| *What causes the checkout page error ERR-4521 and how can it be fixed?* | doc5, doc15_video, doc11_audio | **doc15_video → 10**, doc5 → 10, doc11_audio → 7, doc13_image → 5, doc6 → 2 |
| *How long can a python grow?* | doc12_audio, doc16_video, **doc1 (Python lang)** | doc12_audio → 10, doc16_video → 10, doc2 → 3; doc1 and doc9 dropped |

In the chat UI every answer has two expandable lists: the **re-ranked** chunks the generator saw, and the full **hybrid candidate pool** showing what was dropped. Each hit carries `hybrid_rank` (position from RRF), `score` (RRF score) and `rerank_score` (0–10).

If you'd rather use a local cross-encoder instead of an LLM call, `pymilvus[model]` ships `BGERerankFunction` / `CrossEncoderRerankFunction` with the same "score a list of candidates against a query" shape — swap the body of `rerank_node` in `graph.py`; the rest of the graph doesn't change.

## Chat server (browser UI)

`server.py` wraps the same LangGraph app in a small FastAPI service with a one-page chat UI. It reuses the `hybrid_rag.db` built by `main.py`, so run that once first.

```bash
uvicorn server:app --reload
# then open http://127.0.0.1:8000
```

From the page you can:
- **Type** a question
- **Upload** an audio file (`.wav`/`.mp3`/`.m4a`/`.webm`)
- **Upload an image** (`.png`/`.jpg`/`.webp`) or **a video** (`.mp4`/`.mov`/`.webm`) — anything typed in the box is sent along as a caption
- **Hold the mic button** to record a question in the browser (sent as `.webm`)

Audio/image replies show what Gemini heard or interpreted above the answer, and every reply has an expandable list of the retrieved chunks tagged `text:` / `audio:`. The **Re-index data** button rebuilds the collection from `data/`.

API endpoints (usable with `curl` too):

| Method | Path | Body | Purpose |
|---|---|---|---|
| `POST` | `/api/chat` | `{"question": "..."}` | Typed question |
| `POST` | `/api/chat/audio` | multipart `file=@clip.wav` | Spoken question |
| `POST` | `/api/chat/image` | multipart `file=@shot.png` + optional `question=` | Image question |
| `POST` | `/api/chat/video` | multipart `file=@clip.mp4` + optional `question=` | Video question |

## How multimodal ingestion works

Milvus itself doesn't "understand" audio — it only stores and searches vectors. The multimodal step happens **upstream, in Gemini**:

```
audio file → Gemini (native audio understanding) → transcript text
                                                          │
                                       same path as text docs from here:
                                                          ▼
                                      embed (dense) + BM25-index (sparse)
                                                          ▼
                                              one Milvus collection
```

`gemini_client.transcribe_audio()` sends the raw audio bytes straight to `gemini-flash-latest`, which supports audio as a native input type — no separate speech-to-text service needed. The returned transcript is then treated exactly like any text document: it gets a dense embedding and an auto-computed BM25 sparse vector, and gets tagged `modality="audio"` and `source="<filename>"` so you can see where a retrieved chunk came from.

This means: **one retrieval pipeline, one ranker, results from either modality side by side** — a query can be answered by a sentence that originally lived in a `.wav` file just as easily as one from a text doc.

To add your own audio: drop `.wav`/`.mp3`/`.m4a` files into `data/audio/` and rerun `python main.py`.

## Asking questions by voice (audio queries)

The graph accepts either a typed `question` or a `question_audio` file path. A conditional entry point routes audio through a `transcribe_question` node first:

```
question        ─────────────────────────┐
                                         ├─► retrieve ─► generate
question_audio ─► transcribe_question ───┘
```

```python
app = build_graph(milvus_client, genai_client)

app.invoke({"question": "How long can a python grow?"})              # typed
app.invoke({"question_audio": "data/audio_queries/query_python_length.wav"})  # spoken
```

`gemini_client.transcribe_query()` uses the same native-audio Gemini call as document transcription, but the prompt asks for a *search-ready question* and normalizes spelled-out identifiers — e.g. "E R R dash four five two one" becomes `ERR-4521` — so the BM25 keyword leg of the hybrid search can still match exact codes. The result state includes the transcribed `question`, so you can see what the system heard.

To try your own voice query, record a clip (or generate one on macOS with `say -o q.aiff "your question" && afconvert -f WAVE -d LEI16@22050 -c 1 q.aiff data/audio_queries/q.wav`) and rerun `python main.py`.

## Images: ingestion and image search

Images follow the same pattern as audio — Milvus never sees pixels, Gemini turns them into text first:

```
image file → Gemini (native vision) → description incl. ALL visible text verbatim
           → dense embedding + BM25 sparse vector → Milvus (modality="image")
```

`gemini_client.describe_image()` asks Gemini to transcribe every piece of visible text exactly (error codes, SKUs, numbers) and then briefly describe the scene. Capturing text verbatim is what makes **keyword** search work on screenshots and labels; the description is what makes **semantic** search work on photos. To add your own images: drop `.png`/`.jpg`/`.webp` files into `data/images/` and rerun `python main.py`.

**Image queries** go through an `interpret_image` node. `gemini_client.describe_image_query()` turns the image (plus an optional typed caption) into one self-contained question that includes the key identifiers visible in the image, and that question then runs through the normal hybrid search:

```python
app.invoke({"question_image": "data/image_queries/query_error_popup.png"})                          # image only
app.invoke({"question_image": "data/image_queries/query_error_popup.png", "question": "How do I fix this?"})  # image + caption
```

Sample images (`data/images/doc13_image.png`, `doc14_image.png`, `data/image_queries/query_error_popup.png`) are mock screenshots rendered by `make_sample_images.py`. `doc14_image.png` is the inventory report for `SKU-88213-XL`: `doc10` (text) only says the SKU was delayed, while the actual numbers (120 expected / 97 counted) exist **only in the image** — so the test question *"How many units of SKU-88213-XL were counted?"* proves image ingestion is contributing answers.

## How hybrid search works here

One Milvus collection, one `hybrid_search()` call, two rankings fused automatically:

- **Dense vector search** — compares the *meaning* of the query embedding against document embeddings. Good for paraphrases, synonyms, concepts.
- **BM25 keyword search** — Milvus tokenizes the `text` field and scores exact term overlap. Good for exact codes, IDs, rare words a dense model might blur.
- **RRFRanker()** — merges both ranked lists (Reciprocal Rank Fusion): a document that ranks high in *either* list gets a strong combined score, no manual weight-tuning needed.

You never compute BM25 scores yourself — it's a `Function` attached to the schema, so it runs inside Milvus on every insert and every query.

## Why Milvus (Lite) for this use case, in simple terms

Think of it like this: a lot of vector DBs are good at *one* kind of search. Milvus lets you do **both in the same query, in one system**, which matters a lot for RAG apps where user questions are unpredictable — sometimes they paraphrase, sometimes they paste an exact error code or product ID.

1. **One database, not two.** Without this, you'd typically run a vector DB for semantic search *plus* a separate keyword engine (like Elasticsearch) for exact matches, then glue the two result lists together yourself. Milvus does both natively in one collection with one `hybrid_search()` call and a built-in fusion ranker (RRF). Less infrastructure, less code to maintain.

2. **BM25 runs inside the database.** The sparse/BM25 vector is generated automatically by a `Function` attached to the schema — you just insert raw text. Some other vector DBs require you to compute and manage sparse vectors yourself (e.g., with a separate splade/BM25 library) before inserting.

3. **Milvus Lite means zero ops for a prototype like this.** It's a pip-installable embedded library — the whole "database" is a local file. You get the exact same API (`pymilvus`) as the production distributed version, so this code runs unchanged if you later point it at a real Milvus cluster or Zilliz Cloud as your data grows from a demo to billions of vectors.

4. **It scales with the same code.** If this app grows from 10 test docs to 10 million support tickets, you don't rewrite the retrieval logic — you swap `MilvusClient("hybrid_rag.db")` for a connection to a Milvus cluster. Some lightweight alternatives (like Chroma) don't have as clear a path to that scale; some managed-only options (like Pinecone) don't let you self-host at all if that's a requirement.

The trade-off worth knowing: for a genuinely tiny, single-machine, low-traffic app, this is arguably more machinery than you strictly need — a simpler library could work too. Milvus earns its place either when you want hybrid (vector + keyword) search without hand-rolling the fusion logic, or when you expect to scale well beyond a prototype.

## Troubleshooting

**`404 NOT_FOUND ... text-embedding-004 is not found`**
Google retired `text-embedding-004` (Jan 2026). This project uses `gemini-embedding-001` instead — make sure your `gemini_client.py` has `EMBED_MODEL = "gemini-embedding-001"`.

**`vector field 'dense' expected dim 768, got 3072`**
`gemini-embedding-001` defaults to 3072 dimensions. `embed_text()` must pass `output_dimensionality=EMBED_DIM` (768) in `EmbedContentConfig` to match the Milvus schema — check that line is present if you see this.

**`vector column must be FixedSizeList, got binary` / background compaction traceback**
A known Milvus Lite issue where `AUTOINDEX` on the BM25 `sparse` field can fail to build on small datasets, especially when reopening a `.db` in a new process. Fixed by using `SPARSE_INVERTED_INDEX` explicitly for the sparse field in `milvus_store.py` (already applied in this version).

**Any schema change**
Delete the local DB and rebuild — Milvus Lite doesn't migrate schemas automatically:
```bash
rm -rf hybrid_rag.db
python main.py
```
